## Versioned authored data (021 Fitch foundation)

Derivation-specific definitions, private reference solutions and reference-check responses live in `@logiclab/contracts/derivation`. Combined owner-library definitions and request/response schemas for truth tables, conceptual questions and derivations live in `@logiclab/contracts/problem-library`. Separate package entries keep the private library union distinct from assignment-supported definitions and let browser consumers load the schemas they use. Root/browser package resolution remains supported through explicit package exports.

`DerivationDefinition` includes:

- `type: "derivation"`, `definitionVersion: 1` and instructor-required `format: "fitch"`.
- `ruleCatalogVersion: 1` and `checkerVersion: 1`, pinned to supported engine semantics. These are compatibility requirements, not a cached validation claim.
- Ordered `premises: [{ id, formula }]` with stable normalized UUIDs, and the target `conclusion`.
- Explicit enabled `rules: [{ id, label }]`. Store effective labels with the problem rather than looking up mutable profile defaults on later reads. Rule IDs determine logic; labels determine presentation. No default permission is inferred.
- A nullable `referenceProof`, using the existing flat, versioned Fitch proof shape. Missing or unfinished references are valid draft data.
- Optional private `explanation`, up to 5,000 characters, reserved for reference-answer reveal.

The statement is bounded by the existing proof budgets (50 premises, 256 characters per formula, at most 64 configured rule entries), and the reference uses the existing proof transport bounds. Blank/malformed formulas and incomplete reference steps can be retained in a draft; syntax, scope, permitted inference and target establishment are checked by the engine before a reference can qualify for publication. Premise IDs and enabled rule IDs must be unique. The application helper checks actual rule-catalog membership and version compatibility; a syntactically valid custom slug is not a supported rule.

There is no client-provided accepted flag or stored checker report in this definition. Extra fields such as `referenceAccepted`, an injected report or custom rule behavior are rejected. Changing premises, target or permissions requires a fresh reference check. The initial format is fixed by the instructor; other formats remain guarded until their own complete adapters/workflows exist.

## Effective labels

The user confirmed rejection of duplicate enabled labels after normalization. Labels are trimmed, nonempty plain text of at most 80 characters; control and invisible formatting characters are rejected. Collision comparison applies Unicode NFKC normalization, collapsed whitespace and JavaScript lowercase matching. For example, `MP`/`mp` and `Modus ponens`/`MODUS  PONENS` collide. Display spelling is otherwise preserved. This is a deterministic comparison policy, not a promise to identify every visual homoglyph in every font/language.

Only effective labels of enabled rules participate. Built-in aliases are suggestions, not alternate accepted rule identities or automatically active shortcuts. Custom labels cannot add behavior or enable rules. Editing a label alone leaves the checker result unchanged because proof steps cite stable IDs. Reusable instructor profile storage and editor interactions are not implemented by this data shape.

## Private references and projections

`validateDerivationDefinition` validates the standalone configuration and supported IDs without demanding a complete proof. `checkDerivationReference` returns either `missing` or a fresh versioned checker report computed from the saved statement, enabled IDs and reference. A checked reference is not necessarily accepted. Publication requires `report.status === "accepted"` inside the owning transaction; an old report or a trusted-looking client field cannot substitute for that check.

`derivationContent` explicitly whitelists the statement, format/version requirements and effective rules. It excludes the reference proof and explanation and returns independent parsed values. Its strict content schema rejects private fields rather than accepting a full instructor definition as ordinary content.

`derivationReferenceSolution` is a privileged helper for a caller that has already authorized answer access. It requires a freshly accepted reference and returns its proof/explanation in a separate strict solution schema. It does not authorize the caller, release grades or expose student-specific diagnostics. Owner-store draft editing retains/views raw unfinished reference work; the solution projection is for accepted reference reveal.

These projections are staged helpers, not live student endpoints. Answer access will remain independent of student-proof feedback and grade release, as agreed. Instructor comments/review grades are not part of a reference definition.

## Original 021 persistence and admission guards

The database's `ProblemDefinition` JSON union now includes an exact `DerivationDefinition` type and matching reference-step/block fields. Transport/database types are checked for mutual assignability. Existing `problems.definition` and `problem_versions.definition` JSONB columns already support the shape, so there is no migration, new column, trigger change or snapshot regeneration.

Private owner DTOs (`LibraryProblemDefinition`, `LibraryProblemDraft`, `LibraryProblemVersion` and create/update schemas) extend the supported library types through the separate `@logiclab/contracts/problem-library` entry. They include the reference and explanation and must never replace ordinary assignment content projections. The existing problem store now creates/reads/edits these drafts, lists private version history and archives/restores them with owner-scoped queries. Drafts retain incomplete statements/references; unsupported rule IDs and invalid configuration fail before commit.

`previewReference(ownerId, problemId)` checks the saved definition and returns its problem ID, source `updatedAt` and a missing-reference state or fresh checker report. Preview writes nothing and remains available for archived drafts. The timestamp identifies the checked snapshot; it is not a publication token. The saved-reference UI discards mismatched source timestamps and cancels requests when its saved snapshot/selection changes. Unsaved edits hide/unmount this checker and clear its report; checking is offered again after a successful save or exact reversion. The reference editor also hides a local report whenever its definition differs from the exact checked snapshot.

Publication locks the parent problem, rejects archived/foreign access and rechecks the exact saved reference before allocating the next immutable version number. Missing, rejected or unassessable references cannot publish. Concurrent edits, archive changes and publication use the same parent lock. Later edits to the statement, labels, rules, reference or explanation cannot change an existing snapshot; database triggers protect the entire version JSON. Failed checks roll back without consuming a number. Safe error mappings provide actionable categories without returning private diagnostics in generic errors.

The demo-scoped store uses the existing workspace transaction and owner binding: successful writes commit with the request; failed publication rolls back earlier writes in that transaction. Direct-store and HTTP tests exercise this behavior; no demo derivation content is seeded.

The active owner HTTP routes use private library request/response schemas from the problem-library entry; root `problemDefinitionSchema`, assignment admission (`supportedProblemDefinition`) and student evaluation remain guarded. Assignment version serialization stays separate from the wider private owner serializer. The frontend lists/inspects saved derivations and history, previews private references, checks the saved reference explicitly and retains publication/archive controls. The form dispatches derivation fields separately from truth-table/conceptual fields. Reference-line/subproof editing is available; statement-only edits still preserve existing reference JSON exactly. Matching frontend/API/contracts builds are required because older library clients cannot parse derivation rows.

The assignment picker filters derivation versions after parsing private pages, preserves pagination and retains supported historical versions regardless of the current draft type. See the [HTTP contract](../api/problem-library-api.md#derivation-authoring-branch-021-http-slice) for saved-reference response/error semantics and policies. Normal truth-table/conceptual workflows and historical results remain unchanged.

## Statement and rule editor

Choose **Derivation** in the library's problem-type selector, then **Fitch** under **Proof format**. The initial statement has no premises, an empty conclusion, no enabled rules and no reference. Add/edit/remove/reorder up to 50 premises; moving/editing preserves IDs and re-adding a removed premise creates a fresh ID. Inputs accept the proof formula bounds and disable browser correction hints. Incomplete or malformed formulas can be saved intentionally; they cannot qualify a reference for publication.

Each of the 19 catalog rules requires explicit permission, including classical rules. Inputs offer canonical labels and aliases as suggestions alongside custom text; saved identities remain the catalog IDs. The frontend imports the immutable catalog through the data-only `@logiclab/logic-engine/proof/rules` entry rather than importing the checker into the editor. Disabling a rule retains its label locally for re-enabling in the same editor; inactive labels are excluded from saved definitions and dirty comparisons. Shared contracts reject normalized enabled-label collisions before save or preview. The server remains authoritative for supported rule identities and publication.

Statement/permission edits preserve the existing reference, even if a removed premise or disabled rule makes it invalid. No citation is silently redirected, formula rewritten or acceptance inferred. The private reference is editable through dedicated controls; explanation edits are separate from conceptual explanations and remain reference-answer content. Changing problem type retains local fields until this editor is replaced, but only the selected definition is saved/compared with its saved baseline. Failed saves retain fields and unsaved-work protection. Archived forms disable authoring; publication/archive controls require clean state. Preview displays the current owner definition without saving or asserting proof acceptance. Explicit **Check current proof** validates unsaved work separately.

## Reference proof editor

Fitch, dependency and tree authoring use **Problem details** and **Reference proof** steps. Confirm each statement premise with **Add premise** or **Update premise**; the untouched next input is not a source. **Continue to reference proof** requires parseable premises/conclusion and seeds a fresh proof only when no reference exists: starting premise lines for Fitch/dependency, or one unverified conclusion root for a tree. Tree statement sources are not automatically inserted as leaves. Entering this step neither saves nor checks the work. Incomplete statements remain explicitly saveable on the details step. Hidden metadata is still validated on save, and the selected step survives successful-save remounts.

The proof table shows confirmed lines, notation, citations and actual nested scope guides. Choose **New line scope**, fill the bottom formula/rule/citations and select **Add line**, or press Enter in the formula input outside composition. **Open subproof** stages an assumption and block together; confirmation enters that scope. Unconfirmed input remains local, blocks saving/checking/step changes and participates in navigation protection. **Discard entry** preserves confirmed work. A stale entry cannot overwrite reloaded work. Adding a line is an editing action, not proof verification or a server save.

Each line's three-dot menu offers editing, movement, insertion and deletion where applicable. **Insert before line …** inherits the target scope; inserting before an opening assumption uses its parent. **Close subproof at line …** records that direct line as the endpoint and returns entry to the parent. The assumption menu offers **Subproof settings**, reopening and whole-subproof deletion. Settings retain explicit parent/end choices and exclude descendant parents; a one-line block may end at its assumption. Unattached blocks retain an inspection/removal path. The checker independently validates order, scope, discharge and rule obligations.

Displayed numbers are positions; premise, step and block UUIDs survive edits, insertion and individual movement. No incoming citation slides to another line. Line/subproof deletion uses a modal; full-reference deletion keeps its existing confirmation. Removing a subtree removes its nested blocks/lines while preserving unresolved incoming references. Subproof settings apply to the local draft immediately, including when Escape closes the dialog. None of these actions saves automatically.

Statement and permission edits preserve the existing reference. A source mismatch offers **Restart reference from statement** with Keep/Restart consent; only confirmed restart replaces the entire proof and its identities with the current premises. Inference mistakes do not trigger automatic replacement. Rules/labels use the grouped permitted-rules modal. Archived authoring stays disabled and merely viewing an archived reference does not seed new work.

Shape-valid malformed drafts remain inspectable and saveable. Duplicate/colliding identities disable structural editing, with explicit full-reference removal available; no automatic re-identification occurs. Existing insertion/count/depth bounds and bounded scope walks remain. Read-only submitted work, instructor review and already-authorized reference views reuse the visual display without editing controls; ambiguous data keeps a safe list fallback.

**Check current proof** runs the bounded checker only on explicit action and reports against the exact local definition. It writes nothing and is not a publication credential. Save with **Save draft**, return to details for **Check saved reference** / **Publish saved draft**, and retain the server's fresh checked-publication rules. Answer/grade disclosure, independent solutions, immutable versions and grading semantics are unchanged. Tree-specific construction follows below.

### Tree reference construction (031)

Tree statement premises use a confirmed source list with edit/move/delete menus. The reference step shows one selected node's fields beside the growing tree. Choose the conclusion root's enabled rule, then its three-dot menu's **New supporting …** or **New branch …** action. Enter the formula and, for a discharged branch, explicitly select its assumption formula and leaf occurrences. **Add node** appends and connects that staged child atomically; **Discard entry** leaves the existing proof untouched. Global **New premise node**, **New assumption node** and **New inference node** create unattached entries for manual connection. Premise copying and conclusion-root changes are explicit actions.

Pending entries block save/check/step changes and finalization in student work and remain protected on navigation. Confirmed edits are local draft changes; checking and saving remain separate. Node deletion uses a modal and preserves unresolved incoming references. Cyclic/shared links and missing roots remain inspectable; ambiguous identities disable structural editing rather than silently repairing data.

Changing the target or an entered premise leaf's source can show **Reference statement mismatch**. Keep retains every node/branch; confirmed restart removes the old tree and creates a fresh unverified conclusion root. Available premises need not all occur in a valid tree, so unused sources alone do not trigger a mismatch. This comparison does not validate inference rules. Read-only published/private references, submitted proofs, instructor review and authorized solutions show the diagram without editing controls; unattached nodes and unsafe layouts retain explicit lists. Reference privacy and explanation disclosure remain unchanged.
